툴 설계

Chapter 3 — Tool Design

⟳ 에이전트와 도구(툴)를 잇는 호출 흐름

툴 설계란 무엇인가

도구(tool)는 모델이 호출해 외부 세계에 작용하는 능력입니다 — 파일을 읽고, 코드를 실행하고, API를 부르고, 검색합니다. 모델은 도구의 스키마(이름·설명·매개변수)만 보고 무엇을 어떻게 부를지 결정하므로, 도구를 어떻게 설계하느냐가 에이전트의 성능을 직접 좌우합니다. 같은 모델이라도 도구가 명확하면 정확히 일하고, 모호하면 헤맵니다.

핵심 개념

도구의 스키마는 모델을 위한 사용설명서입니다 — 사람이 읽기 좋게가 아니라, 모델이 오해 없이 부를 수 있게 써야 합니다.

하 · 입문

한 줄로 이해하기

도구(툴)는 모델이 호출해 쓰는 '버튼'이고, 툴 설계는 그 버튼에 무엇을·어떻게 누르라고 적힌 라벨을 잘 붙이는 일입니다.

왜 흥미로운가?

사람도 처음 보는 기계 앞에서 버튼 라벨이 헷갈리면 엉뚱한 걸 누릅니다. 모델도 똑같아요. 도구 이름이 모호하거나, 매개변수 설명이 빠졌거나, 에러 메시지가 "오류 발생"뿐이면 모델은 추측하다 실수합니다. 놀라운 건 모델을 전혀 안 바꾸고도 도구 라벨만 또렷하게 다시 쓰면 에이전트가 눈에 띄게 똑똑해진다는 점입니다.

🌱 핵심 용어

  • 도구(Tool): 모델이 호출하는 외부 능력(검색·실행·파일)
  • 스키마(Schema): 도구의 이름·설명·매개변수 정의
  • 입도(Granularity): 도구를 얼마나 잘게/크게 나눌지
  • 멱등성(Idempotency): 같은 호출을 여러 번 해도 결과가 같음
  • 부작용(Side effect): 세상을 바꾸는 행동(파일 삭제·메일 발송)

개념 풀어쓰기

리모컨을 떠올려 봅시다. 버튼이 너무 많고 라벨이 작으면 원하는 기능을 못 찾고, 버튼 하나에 기능 열 개가 묶여 있으면 무엇을 누를지 막막합니다. 좋은 리모컨은 자주 쓰는 동작을 또렷한 라벨로, 적당한 개수로 제공합니다. 도구 설계도 같습니다. 이름은 동작을 분명히 드러내고(예: 'send_email'은 좋고 'do_action'은 나쁨), 설명은 언제 쓰는지·언제 쓰지 말지를 알려 주며, 매개변수는 무엇을 넣어야 하는지 한 글자도 헷갈리지 않게 적습니다. 그리고 실패하면 "오류"가 아니라 "이메일 주소 형식이 잘못됨: '@'가 없음"처럼 모델이 스스로 고칠 수 있는 메시지를 돌려줘야 합니다.

💡 학습 TIP: 좋아하는 앱의 버튼·메뉴 이름을 보며 "처음 본 사람이 무슨 일을 하는지 바로 알까?"를 자문해 보세요. 그 직관이 곧 좋은 도구 이름의 기준입니다.

요약

  • 도구는 모델이 호출하는 외부 능력입니다.
  • 모델은 스키마(이름·설명·매개변수)만 보고 부릅니다.
  • 이름·설명·매개변수가 명확해야 모델이 안 헤맵니다.
  • 에러는 모델이 고칠 수 있게 구체적으로 돌려줍니다.
  • 도구를 너무 잘게도, 너무 크게도 나누지 않습니다.
중 · 응용

메커니즘 깊이

모델은 도구를 직접 실행하지 않습니다. 모델이 도구 호출(예: read_file(path="src/app.py"))을 구조화된 출력으로 내면, 하네스가 그 인자를 받아 실제 함수를 돌리고 결과를 다시 컨텍스트에 넣습니다. 따라서 도구 설계의 핵심은 세 면입니다. ① 스키마: 이름·설명·매개변수 타입·필수 여부를 정의해 모델이 '무엇을 어떻게'를 알게 합니다. ② 반환값: 성공 결과뿐 아니라 실패도 모델이 행동을 교정할 수 있는 형태로 돌려줍니다. ③ 입도: 한 도구가 책임지는 범위. 너무 잘게 나누면 호출이 폭증하고(왕복마다 토큰·지연 발생), 너무 크게 묶으면 모델이 어떤 모드로 부를지 헷갈립니다. 또한 멱등성(같은 호출을 반복해도 안전)과 부작용(되돌릴 수 없는 행동) 구분이 중요합니다 — 에이전트는 재시도를 자주 하므로, 멱등하지 않은 부작용 도구는 중복 실행 위험을 안습니다.

🛠️ 사례 1 — 에러 메시지가 성능을 바꾼다

도구가 실패할 때 "Error"만 돌려주면 모델은 원인을 추측하다 같은 실수를 반복합니다. 대신 "파일을 찾을 수 없음: 'src/app.py'. 디렉터리에 있는 파일: app.js, main.py"처럼 다음 행동의 단서를 담으면, 모델은 스스로 경로를 고쳐 재시도합니다. 에러 메시지는 모델을 위한 디버깅 힌트입니다.

🛠️ 사례 2 — 입도의 균형

'한 글자 쓰기'처럼 너무 잘게 나눈 도구는 한 작업에 수백 번 호출을 유발해 느리고 비쌉니다. 반대로 '아무거나 다 하는 do_everything' 도구는 모델이 인자를 어떻게 채울지 몰라 실패합니다. 좋은 입도는 사람이 '한 동작'으로 떠올리는 단위(파일 읽기, 패치 적용, 검색 1회)에 맞춥니다.

설계 관점

도구는 모델의 '시야'를 정의합니다. 도구가 곧 에이전트가 할 수 있는 일의 경계이므로, 새 능력을 더하는 가장 빠른 길은 모델 교체가 아니라 좋은 도구를 추가하는 것입니다. 동시에 도구 설명은 컨텍스트를 차지하므로, 수십~수백 개 도구를 한꺼번에 노출하면 토큰을 낭비하고 모델의 선택을 어렵게 합니다 — 그래서 대규모 툴셋에서는 도구를 지연 로딩하거나 검색해 필요한 것만 보여 줍니다.

⚠️ 자주 하는 오해: "도구는 많을수록 좋다"는 틀렸습니다. 도구가 많아질수록 설명이 컨텍스트를 잠식하고, 비슷한 도구끼리 모델을 헷갈리게 하며, 선택 실수가 늘어납니다. 핵심은 개수가 아니라 각 도구의 명확함과 적절한 입도입니다.

상 · 심화

전문가 레벨 — 도구는 모델-환경 인터페이스다

도구 설계는 사실상 모델과 환경 사이의 API 설계입니다. 일반 API와 다른 점은, 사용자가 사람이 아니라 확률적으로 인자를 채우는 모델이라는 것 — 그래서 모호함은 곧 오류율로 직결됩니다. 실전 원칙: (1) 명료한 이름·설명으로 도구 간 혼동을 없앤다. (2) 실패를 행동 가능한 신호로 설계한다(원인+다음 단계). (3) 입도를 작업 단위에 맞춘다 — 호출 폭증과 과적재 사이의 균형. (4) 멱등성·부작용을 명시하고, 되돌릴 수 없는 행동은 확인 게이트나 드라이런을 둔다. (5) 대규모 툴셋은 동적으로 노출한다(툴 서치·지연 로딩·관련 도구만 주입).

핵심 트레이드오프

툴 호출 성공률 ≈ f(스키마 명료도, 에러 행동성, 입도 적합도, 노출 도구 수의 절제, 부작용 안전장치)

입도에는 정량적 긴장이 있습니다. 도구가 N배 잘아지면 같은 작업의 호출 수와 왕복 토큰이 대략 그만큼 늘어 지연·비용이 커지고, 반대로 너무 굵으면 인자 공간이 넓어져 모델의 인자 충전 오류가 늘어납니다. 또한 노출하는 도구 수가 많을수록 스키마가 컨텍스트를 잠식하고, 의미가 겹치는 도구는 선택 분산을 키웁니다. 그래서 '필요한 도구만, 명확하게, 알맞은 크기로'가 설계의 축입니다.

최신 흐름

도구 호출(function/tool calling)은 모델 API의 표준 기능이 되었고, MCP(Model Context Protocol) 같은 개방 프로토콜로 도구를 서버처럼 표준화해 연결하는 흐름이 뚜렷합니다. 수백 개 도구를 다루는 에이전트가 늘면서, 모든 도구를 항상 노출하는 대신 도구를 검색/지연 로딩해 컨텍스트를 절약하는 기법이 보편화되고 있습니다.

관련 분야

  • API/인터페이스 설계 및 스키마(JSON Schema)
  • MCP·함수 호출 등 도구 연결 표준
  • 분산 시스템의 멱등성·재시도·부작용 처리
