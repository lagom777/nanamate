1. 인증(AuthN) vs 인가(AuthZ) — 둘은 다르다

현장에서 가장 자주 혼동되는 두 단어는 인증(Authentication)과 인가(Authorization)입니다. 인증은 "당신이 누구인지" 증명하는 절차이고, 인가는 "당신이 무엇을 할 수 있는지" 결정하는 절차입니다. 공항 비유로 말하면, 여권 검사는 인증, 1등석 라운지 입장 가능 여부는 인가입니다. 둘은 분리되어 설계되어야 하며, 같은 시스템이 둘을 같은 코드 경로에서 처리하면 거의 반드시 버그가 생깁니다.

인증의 세 가지 요소(factor)는 ① 지식(knowledge, 비밀번호·PIN), ② 소유(possession, 휴대폰·하드웨어 키), ③ 생체(inherence, 지문·얼굴)입니다. 이 중 둘 이상을 결합하면 MFA(Multi-Factor Authentication)가 되며, 같은 요소의 두 개(예: 비밀번호 두 개)는 MFA가 아닙니다.

2. 비밀번호 — 여전히 가장 약한 고리

비밀번호는 30년 넘게 폐기 선고를 받아왔지만 여전히 가장 보편적인 인증 수단입니다. 안전한 저장의 표준은 솔트(salt)와 의도적으로 느린 KDF의 결합이며, 2025년 기준 권장은 Argon2id(2015 PHC 우승, RFC 9106)입니다. bcrypt는 여전히 안전하나 메모리 강성이 약하고, scrypt는 ASIC 저항성에서 더 우월합니다. 일반 SHA-256만으로 비밀번호를 저장하는 것은 GPU·ASIC 무차별 대입에 무력하므로 절대 사용 금지입니다.

NIST SP 800-63B(2017, 2024 개정)의 권고는 직관과 다릅니다: ① 주기적 변경 강제 금지(유출 의심 시에만), ② 복잡도 규칙(특수문자 강제 등) 폐지, ③ 길이만 강조(최소 8자, 권장 15자+), ④ 침해된 비밀번호 사전(HIBP API) 대조, ⑤ rate limiting과 lockout 정책으로 무차별 대입 방어. 이 권고는 사용자 행동 연구에 기반하며, 강요된 복잡도가 오히려 약한 패턴(Password1!)을 유도한다는 것이 이유입니다.

3. OAuth 2.0 · OIDC · JWT

OAuth 2.0(RFC 6749, 2012)은 인가 위임을 위한 프레임워크입니다. "구글로 로그인"이 대표 사례로, 사용자가 자신의 비밀번호를 제3자에게 노출하지 않고도 일부 권한만 부여할 수 있습니다. 4가지 grant 중 현재 권장은 PKCE를 결합한 Authorization Code Flow이며, Implicit Flow는 폐기되었습니다.

OAuth 자체는 인증이 아닌 인가 프로토콜입니다. 인증을 표준화한 것이 OpenID Connect(OIDC, 2014)로, OAuth 2.0 위에 ID Token(JWT 형식)을 추가합니다. JWT(JSON Web Token, RFC 7519)는 header.payload.signature 3부분으로 구성된 자체 검증 가능한 토큰이며, 서명 알고리즘은 alg: HS256(HMAC) 또는 RS256/ES256(비대칭)을 사용합니다. 절대로 alg: none은 허용하면 안 됩니다 — 2015년 다수 라이브러리에서 발견된 치명적 취약점입니다.

4. 인가 모델 — RBAC, ABAC, ReBAC

인가 모델은 권한을 어떻게 정의하고 평가할지의 문제입니다. RBAC(Role-Based)는 사용자에게 역할(admin·editor·viewer)을 부여하고 역할에 권한을 묶는 방식으로 가장 흔합니다. ABAC(Attribute-Based)는 사용자·자원·환경 속성을 정책 엔진(XACML·OPA)에 넣어 동적으로 결정합니다. ReBAC(Relationship-Based)는 구글이 Zanzibar 논문(2019)에서 정립했고, 사용자-자원 간의 관계 그래프로 권한을 표현합니다. SpiceDB·OpenFGA가 오픈소스 구현이며 Notion·GitHub 같은 협업 도구에 적합합니다.

현장 권고는 단순합니다: ① 작은 시스템은 RBAC로 시작, ② 다차원 정책이 필요하면 OPA(Open Policy Agent)로 ABAC 확장, ③ 공유·계층 관계가 핵심이면 SpiceDB로 ReBAC. 어느 모델이든 최소 권한 원칙(Principle of Least Privilege)이 깔려 있어야 합니다.

  • 인증(AuthN): "너 누구야?" — 비밀번호, 지문, 문자
  • 인가(AuthZ): "너 뭐 할 수 있어?" — 관리자냐 일반 회원이냐

  • 패스키(Passkey): 비밀번호를 대신하는 새 방법

🏢 회사 출입으로 이해하기

중 · 응용

이론 깊이 들어가기

OAuth 2.0의 보안 모범사례는 OAuth 2.0 Security Best Current Practice(RFC 9700, 2025)로 정립되어 있습니다. 핵심: ① Implicit·ROPC grant 폐기, ② Authorization Code + PKCE를 모든 클라이언트에 의무화(공개·기밀 무관), ③ Redirect URI 엄격 매칭(부분 매칭 금지), ④ state·nonce 파라미터로 CSRF·재전송 방어, ⑤ refresh token 회전(rotation)과 detection, ⑥ DPoP·mTLS로 토큰 도난 방지. OAuth 2.1 드래프트는 이 권고를 통합한 차세대 사양입니다.

세션 관리도 인증의 핵심입니다. 서버 측 세션(쿠키에 session ID, 서버 메모리/Redis에 상태)과 JWT 같은 stateless 토큰은 트레이드오프가 다릅니다. 서버 세션은 즉시 무효화 가능하지만 수평 확장이 부담, JWT는 stateless라 확장이 쉽지만 로그아웃·권한 변경 즉시 반영이 어렵습니다. 실무는 둘을 혼합합니다: 짧은 access token(15분) + 긴 refresh token(7일~30일) + 서버 측 revocation list.

핵심 코드 — JWT 검증

# PyJWT — 안전한 JWT 검증
import jwt
from jwt.exceptions import InvalidTokenError

def verify_jwt(token: str, public_key: str) -> dict:
    try:
        payload = jwt.decode(
            token,
            key=public_key,
            algorithms=["RS256"],           # ⚠️ 명시 필수, "none" 절대 허용 X
            audience="https://api.example.com",
            issuer="https://auth.example.com",
            options={
                "require": ["exp", "iat", "sub", "aud", "iss"],
                "verify_exp": True,
                "verify_iat": True,
                "verify_signature": True,
            },
            leeway=30,  # 시계 오차 30초 허용
        )
        return payload
    except InvalidTokenError as e:
        raise PermissionError(f"Invalid token: {e}")

# Argon2id — 안전한 비밀번호 저장
from argon2 import PasswordHasher
ph = PasswordHasher(time_cost=3, memory_cost=64*1024, parallelism=4)
hashed = ph.hash("user-password-here")
ph.verify(hashed, "user-password-here")   # 일치 시 True, 아니면 예외

대표 예제

🔑 예제 1 — 2022 Okta 침해와 SAML

2022년 1월 Lapsus$ 그룹이 Okta(글로벌 IdP)의 협력업체 직원 PC를 통해 일부 고객 데이터에 접근했습니다. 직접 침해는 좁았지만, IdP 침해의 파급효과는 막대했고 SAML·SCIM·SSO의 신뢰체인 전체가 점검되었습니다. 교훈: SSO는 매우 강력하지만 동시에 단일 실패점이 되며, IdP 자체에 대한 다층 방어(직원 MFA·기기 신뢰·세션 모니터링)가 필수입니다.

🔑 예제 2 — Passkey로 로그인

WebAuthn(W3C, 2019) + FIDO2 CTAP2를 결합한 Passkey가 2022년부터 Apple·Google·Microsoft에서 동시 지원되었습니다. 사용자 디바이스가 키 쌍을 생성·저장하고, 서버에는 공개키만 등록됩니다. 로그인 시 챌린지를 서명하는 방식이라 ① 비밀번호 유출 불가, ② 피싱 저항성(도메인 바인딩), ③ MFA 내장의 세 마리 토끼를 잡습니다. 2024년 Google은 14억 개의 Passkey가 발급되었다고 발표했습니다.

응용 사례

① SCIM(System for Cross-domain Identity Management): 사용자 프로비저닝·디프로비저닝 표준. Okta·Azure AD·Workspace의 자동화 핵심. ② Step-up Authentication: 평소엔 단순 인증, 고위험 작업(송금·설정 변경) 시에만 MFA 재요청. ③ Risk-based MFA: 평소와 다른 위치·기기·시간 패턴 감지 시 자동 MFA. ④ Service Account 관리: 사람이 아닌 시스템 간 인증은 mTLS · workload identity(SPIFFE/SPIRE) · IAM roles로 자동 발급/회전.

⚠️ 자주 하는 실수: ① JWT를 localStorage에 저장 → XSS 한 방에 탈취 (가능하면 HttpOnly cookie). ② Refresh token을 그대로 재사용 (rotation + detection 필수). ③ 인가 결정을 클라이언트에서 (UI 숨김만으로 안전하다고 착각). ④ 비밀번호 재설정 토큰을 무제한 유효로 설정. ⑤ "잠금"이 무차별 대입을 막을 뿐, 분산 공격(credential stuffing)은 못 막음 — HIBP 매칭이 추가로 필요.
상 · 심화

전문가 레벨 이해

현대 인증·인가의 패러다임은 Identity-Aware Proxy(IAP)와 Zero Trust로 수렴합니다. 모든 요청은 네트워크 위치와 무관하게 사용자·기기·세션 컨텍스트를 평가받습니다. Google BeyondCorp(2014~)이 산업적 선례를 만들었고, Cloudflare Access·Tailscale·Cisco Duo 등이 대중화했습니다. 핵심 구성은 PDP(정책 결정)·PEP(정책 시행)·PIP(정책 정보)·PAP(정책 관리)의 4요소이며, OPA(Open Policy Agent)와 Rego 언어가 사실상의 표준 PDP가 되었습니다.

워크로드 신원(Workload Identity)은 사람이 아닌 서비스 간 인증의 새 표준입니다. SPIFFE/SPIRE(CNCF 졸업 프로젝트)는 SVID(SPIFFE Verifiable Identity Document, X.509 또는 JWT)를 자동 발급하고 짧은 TTL로 회전합니다. 클라우드 별로는 AWS IAM Roles for Service Accounts, GCP Workload Identity Federation, Azure Managed Identity가 동등한 기능을 제공합니다. 이로써 비밀번호·API 키의 정적 저장이 사라지고, 모든 자격증명이 동적·단기·검증가능해집니다.

수학적·정량적 기초

$$\text{Password entropy: } H = L \cdot \log_2(N), \quad \text{(L=길이, N=문자집합)}$$ $$\text{Brute force time: } T = \frac{N^L}{2 \cdot R}, \quad \text{(R=초당 시도, 평균은 } N^L/2 \text{)}$$ $$\text{Argon2 cost: } \text{Memory} \times \text{Iterations} \times \text{Parallelism}$$

예를 들어 8자 영숫자 + 특수문자(N=94)의 엔트로피는 약 52.5비트, GPU 100억회/초로 약 2일이면 깨집니다. 동일 자원에 Argon2id(64MB·3회·4스레드)를 적용하면 단일 GPU가 초당 수백 회로 떨어져 같은 8자도 수십~수백 년이 걸립니다. 즉 KDF가 사실상 의 비밀번호 길이를 수십 비트 더하는 효과를 냅니다.

최신 연구와 frontier

① Verifiable Credentials & DID: W3C DID(Decentralized Identifier) v1.0(2022), Verifiable Credentials v2.0이 표준화되어 자기주권 신원(Self-Sovereign Identity)이 실용 단계로. EU eIDAS 2.0 디지털 신원 지갑(EUDI Wallet, 2026)이 대표 사례. ② Continuous Access Evaluation Protocol(CAEP): Shared Signals Framework로 위험 신호(세션 폐기·토큰 회수)를 IdP↔RP 간 실시간 전파. Microsoft·Google·Cisco가 주도. ③ Privacy-Preserving Authentication: BBS+ 서명, anonymous credentials(IBM Identity Mixer), zk-SNARK 기반 ID(zkLogin)로 "신원 노출 없이 자격 증명". ④ OAuth 2.1 + GNAP: Grant Negotiation and Authorization Protocol(IETF)이 OAuth의 다음 세대로 부상.
